# Handover

Everything a new teammate needs to understand, run, demo and extend Saint Elms Fire without reading the code first. Start with [README.md](README.md) for the pitch. A coding agent should read [AGENTS.md](AGENTS.md) first (commands, invariants, definition of done). The deep references are [docs/agentic-layer.md](docs/agentic-layer.md) (teachers, tools, harness, sources, chat history) and [docs/knowledge-graph.md](docs/knowledge-graph.md) (course sky, second brain, mastery).

---

## 1. Concepts in one page

| Term | Meaning |
| --- | --- |
| **University (uni) server** | The institution's side. It owns accounts, cohorts, which courses are released to which cohort, signs course packages, relays peer shares, and serves the registrar's API. |
| **Engine** | The student's local runtime (a Node process on their device). It runs the teachers, keeps the brain, syncs courses and works offline. The desktop UI only ever talks to the engine, except for the registrar app. |
| **Profile / workspace** | One student on a device. Each has its own folder: `.data/engine/profiles/<id>/{content,brain,sessions,quizzes}`. Several students can share a device without seeing each other's data. |
| **Cohort** | An intake year (`bsc-pma-2024`, `-2025`, `-2026`). Releases are set per cohort. |
| **Release** | The registrar switches a course on for a cohort. Only released courses appear in a student's Library and can be installed. |
| **Course package** | A course's lessons plus a manifest of SHA-256 hashes, signed with the university's ed25519 key. The engine pins the key on first sync and rejects anything that doesn't verify. |
| **Dispersal** | Which version of each course each student has installed, so the registrar can see who is out of date. Devices report it on every catalogue check. |
| **Second brain** | A markdown vault of typed wiki pages. Models draft; the compiler normalizes them into proposals, and nothing writes until the student reviews and accepts one — there is no auto-commit path. |
| **Mastery** | `unseen` / `met` / `shaky` / `solid`, computed from evidence (quizzes, open misconceptions). Never written by a model. |
| **Sky** | The visual map of every course concept. Stars light up as the brain grows; aurora lines are links the student made. |
| **Reflect** | After a chat, freeze the new turns as a session source. The compile it later produces files a proposal; the student sees the diff in the review dialog before anything lands. |
| **Contribute** | The "Add to my wiki" desk: write or paste text, upload a photo/PDF, or take a conversation as the source. Every contribution is retained as an immutable source with its provenance (own thinking vs external), extraction can be corrected, and a compile always ends in an explicit proposal review. |
| **Peer share** | An admitted student publishes a page to their cohort's feed; publication is idempotent, quota-limited, and withdrawable. Staff can remove shares with an audit trail. |
| **Sources** | The lessons, brain pages and web results behind an answer. Lesson sources are checked against the finished answer: only lessons it measurably drew on are shown as cited, and each links to the exact section of the lesson. |
| **Chat history** | Every conversation is saved as JSON in the student's workspace, including each answer's sources and checks. Reopen it from History; a reload restores the open conversation. |

## 3. Running it

**Prerequisites:** Node 22+, pnpm (via `corepack enable`), Ollama with `gemma4:e4b`, and Docker (optional, for SearXNG or the full stack). Rust is needed only for `pnpm desktop`.

```bash
pnpm install
cp .env.example .env     # optional: every value has a default
pnpm ollama:pull         # pulls the default Gemma 4 model
pnpm search:up           # SearXNG on :8888 (the Philosopher degrades gracefully without it)
pnpm dev                 # uni :4200, engine :4100, UI :5173
pnpm preflight           # green/red checklist before a demo
```

**Self-hosted stack:** `pnpm docker:up` runs the uni server, SearXNG and the engine. Add the Ollama container with `docker compose --profile ollama up -d`.

**Where data lives:**
- uni server: `.data/uni/` (accounts, releases, dispersal, shares, `audit.jsonl`) and `server/uni/keys/` (the signing key, created on first boot);
- engine: `.data/engine/` (`profiles.json` and `auth-sessions.json` hold device auth state; `settings.json` holds shared server endpoints and any legacy device settings; `trust/` pins the university key; `profiles/<id>/{content,brain,sessions,quizzes}/` is portable student data, while `profiles/<id>/private-settings.json` holds new per-profile model choices and provider credentials. Legacy provider keys are not copied to a student profile automatically.

Legacy anonymous folders at `.data/engine/{content,brain,sessions,quizzes}/` are never assigned at sign-in. After signing in to the intended profile, use `GET /api/anonymous-data` to preview, `POST /api/anonymous-data/backup` to create a safety copy, and `POST /api/anonymous-data/claim` with that response’s `backupId` to import. The original folders remain unchanged; the backup includes only those four data categories, never auth or provider secrets.

**Resetting the demo:** stop everything and delete `.data/engine/` and `.data/uni/`. Both services re-seed the demo accounts on the next boot, and the engine regenerates the three brains, which is deterministic, so you get the same demo every time. Keep `server/uni/keys/` unless you also want to reset the pinned key. If you delete the keys, delete the engine data as well, or sync will (correctly) refuse the new key.

## 5. Suggested demo script (about 7 minutes)

1. **Sign in** via *Exploring the demo? → First-year student*. Mention that the university verifies the sign-in and that the device keeps an offline verifier.
2. **Sky.** Mechanics is half lit and the amber stars are her misconceptions. Click one: the panel shows "in my words" and the open misconception.
3. **Guide.** Ask "why does a moving thing need a force to keep moving?". Watch the thought trace (steps and timer). It answers from her lessons, names the misconception and asks a checking question. Then:
   - click a **lesson source chip** to see the exact passage used, then **Open at this section** to jump into the lesson;
   - point out "+1 also retrieved": a lesson that was looked at but not used;
   - open the **checks** chip: every citation resolved against this teacher's evidence, factual statements backed before they were shown, tool calls, and the model running on-device.
4. **Reflect** the session. The turns freeze as a source; open **Add to my wiki** and show the job run, then the proposal review — what would land, what was dropped, and why — and accept it there.
4a. **History.** Reload the page: the conversation is still there. Open **History** to show saved conversations, including the seeded ones and the "not reflected" badges.
5. **Philosopher.** Ask about the same idea in the real world. Point out the `[course]`/`[web]` tags and the trailhead.
6. **Friend.** Ask for a classmate's phone number. It refuses instantly, without calling the model.
7. **Switch to Brinda, then Chetna.** Same Mechanics course, three different skies.
8. **Offline.** Stop the uni server, sign out, and sign back in: *Signed in offline*, and everything still works.
9. **Registrar.** Sign in as admin. Toggle a release for a cohort, open **Dispersal** to see stale devices, then **Audit** to see the action logged.

## 6. Auth and offline, precisely

- **Online student sign-in:** the engine forwards the credentials to the uni server and gets back a signed student token. It caches the profile and a **scrypt verifier** of the password in `profiles.json`, then issues its own engine session token to the UI.
- **Offline sign-in:** if the uni server can't be reached (network error only, never on a wrong password), the engine checks the cached verifier. A profile that has never signed in online on this device can't sign in offline.
- **Engine sessions** last `ENGINE_SESSION_HOURS` (14 days by default). A 401 from the engine logs the UI out.
- **The uni token** lasts `STUDENT_TOKEN_HOURS` (30 days) so devices can sync after weeks offline. If it expires, the Library shows a "sign in while online" prompt; studying still works.
- **Registrar:** the UI talks to the uni server directly with a short-lived admin token (`ADMIN_TOKEN_HOURS`). Every admin write goes to `audit.jsonl`.
- **Account endpoints (PR-04):** with `UNI_DATABASE_URL` set and migration 002 applied (`docker compose run --rm uni pnpm --filter @sef/uni-server db:migrate`, or `pnpm --filter @sef/uni-server db:migrate` with `UNI_DATABASE_URL` for a host-run server), the uni server mounts better-auth under `/v1/auth/*`: email/password with required verification, magic links, password recovery and session revocation. Required configuration is `UNI_PUBLIC_URL` (the canonical origin used in account emails and trusted-origin checks), `BETTER_AUTH_SECRET` (32+ characters, required in production), and real SMTP in production (`MAIL_SMTP_URL`; `MAIL_FROM` optionally overrides the default sender). `UNI_TRUSTED_ORIGINS` may add extra redirect origins. In development, start Mailpit (`docker compose --profile mail up -d mailpit`, UI at http://127.0.0.1:8025); a host-run server uses the loopback default, while the Compose `uni` container needs `MAIL_SMTP_URL=smtp://mailpit:1025` in `.env` to reach it. Magic links expire in 15 minutes, are stored hashed, and are consumed atomically; the emailed link opens a confirmation page (`/v1/auth/magic-link/confirm`) whose form POSTs the token back to the server, so GET requests — including mail scanners and prefetchers — never consume it. Exercise the disposable database suite with `pnpm --filter @sef/uni-server db:test:integration`. Registration grants no admission or staff privilege: authentication is not admission, and onboarding that collects the required profile fields and notices arrives in PR-05/09 — do not roll these endpoints out to production before PR-05 and PR-07. Without a database these endpoints answer 503 and the legacy token login and offline sign-in above are unaffected.
- **Admission and staff administration (PR-05):** with `UNI_DATABASE_URL` set and migration 003 applied, a verified account can apply to the programme (`POST /v1/applications`), see its own state (`GET /v1/me`), withdraw (`POST /v1/me/enrolment/withdraw`) and file an erasure request (`POST /v1/me/erasure-requests`). Staff APIs live under `/v1/admin/`: student search/detail/patch (`/students`), enrolment decisions (`/enrolments/:id/decision`), staff membership (`/staff`), recovery-email relay, erasure confirmation and `audit-events`. All of it requires a live better-auth session with an active `staff_memberships` row; mutating routes additionally require a session created within the last 30 minutes (`reauthentication_required` otherwise) and optimistic `expectedVersion` values on decisions and profile patches. Only owners can grant or modify owner memberships, and the last active owner can never be suspended or ended. Bootstrap the first owner from the operator shell — there is no HTTP path: `UNI_DATABASE_URL=… pnpm --filter @sef/uni-server staff:grant -- --email ops@uni.edu --role owner`. Suspending a student profile, an enrolment or a staff membership revokes that account's sessions through the auth adapter (sessions live in `auth_kv` secondary storage; a raw `session`-row delete is not enough). `/v1/programme` now serves the full manifest to approved students and any staff session; packages and cohort data stay release-gated. Admission rows are audited in `audit_events`; without a database every admission surface answers 503.
- **Device sign-in and offline entitlement (PR-07):** first-party sign-in for enrolment accounts uses RFC 8628 device authorization: the engine calls `POST /api/auth/device/start` (returns a `userCode` and the uni's `verificationUri`, better-auth `/v1/auth/device/*`), the student confirms the code on the uni page, and the UI repeats `POST /api/auth/device/poll` until `approved`, `denied` or `expired` (`slow_down` widens the interval hint). Approval yields a uni session, the recorded `admission` state — and, for approved students, an engine session plus a **signed offline entitlement** (`POST /v1/entitlement`, ~24 h via `ENTITLEMENT_HOURS`, bound to `aud=sef-engine`, the student, this device and the cohort). Pending students get a session that reaches only `/api/auth/*` — every data, settings and SSE route answers `403 unapproved`. Offline re-entry for device profiles is `POST /api/auth/offline-login`, which verifies the stored entitlement locally (signature against the pinned uni key, audience, student, device); an *expired* entitlement still unlocks private read/export because the student's own files stay theirs. Secrets — uni session tokens, entitlements, legacy uni tokens — live in the OS credential store (Keychain on macOS, `secret-tool` on Linux) or memory only; nothing plaintext in `profiles.json`, `auth-sessions.json` (sessions are SHA-256-keyed), settings or browser storage (the UI keeps tokens in `sessionStorage`). The engine refuses non-loopback `Host` headers, rejects mutating requests carrying a foreign `Origin` (allowed: the Vite dev origin and Tauri schemes, extendable via `ENGINE_ALLOWED_ORIGINS`), caps bodies at 20 MB, narrows CORS to the same allowlist, and the Tauri CSP permits only `https:` plus loopback connections. Device tokens never authorize staff APIs — every `/v1/admin` route demands a live staff session. Signing out revokes all of the profile's engine sessions, deletes stored credentials, best-effort signs the uni session out, and drops the cached workspace.

- **Onboarding and the university-hosted portal (PR-09):** account and admission work moved off the engine's password form onto two surfaces the uni server hosts itself, so the better-auth session cookie is same-origin and no credential ever passes through the desktop app. `GET /device` serves a standalone confirmation page (`?user_code=…`) whose Approve/Deny buttons POST to `/v1/auth/device/approve` and `/v1/auth/device/deny` with the session cookie; it carries a per-response CSP nonce, `no-store`, `frame-ancestors 'none'` and `Referrer-Policy: strict-origin`, reads the code from the query string in script (never into markup), and clears it from the address bar. `GET /app/*` serves the onboarding shell built by `pnpm --filter @sef/desktop build:portal` into `apps/desktop/dist-portal` (override with `UNI_PORTAL_DIR`), hashed assets cached immutably and everything else revalidated. Both surfaces resolve inside the portal root only — traversal and symlinks that leave it are refused — and both answer `503 account_auth_unavailable` when no database is configured, so an unbuilt or unconfigured portal can never look like a working one. The desktop sign-in screen is now an RFC 8628 device grant (`/api/auth/device/start`, poll on the server's interval, cancel, honest denied/expired outcomes) plus offline unlock for profiles already signed in here; the engine derives `admission` and `Root` refuses the dashboard for `pending`/`rejected`/`suspended`/`withdrawn`, showing a state screen with a link back to `/app` instead. `approved` — and legacy/demo profiles that predate the gate — reach the dashboard unchanged. React Query keys are prefixed by profile id and in-flight queries are cancelled before the cache is cleared, so a late response from one student can never appear under the next. Set `VITE_UNI_URL` for the portal link. Demo personas still sign in locally and deliberately bypass admission.

- **Signed academic metadata and atomic installs (PR-08):** the package manifest now carries the course's academic metadata (title, subject, semester, credits, hours, delivery mode, status, option group, prerequisites, lesson count) under `schemaVersion: 2`, and the ed25519 signature covers it — so a corrected credit total or a renamed course is as tamper-evident as the lesson files. `deriveContentVersion(files, metadata)` folds both into the content version, so a metadata-only correction changes the version and forces a re-sync instead of leaving devices silently stale; the catalogue reports exactly the version the package carries (the engine refuses a manifest whose version disagrees with its own contents). The engine verifies everything *before* touching disk: issuer, course id, schema generation, signature, unique manifest paths, the exact file set in both directions, declared byte length, SHA-256 per file, traversal-safe paths, and the derived version. Install is atomic — the new tree is staged beside the live one and swapped with a rename, with rollback — so a failed or interrupted install leaves the previous working courseware exactly as it was instead of half-replaced. The issuer anchor is TOFU-pinned beside the signing key from `/v1/keys` (`trustedUniIssuer`), so an unreachable uni or an issuer-less answer aborts the install rather than weakening the check. Schema-1 manifests (file hashes only, no signed metadata) still install but are recorded with `signedMetadata: false` and logged as `package_installed_without_signed_metadata`, so a legacy install is never presented as fully verified until the next sync.
- **Staff portal (PR-10):** `apps/admin` is its own workspace package, built with `pnpm --filter @sef/admin build` into `apps/admin/dist` and served by the uni at `/admin` (override with `UNI_ADMIN_DIR`), reusing the same hardened CSP and the traversal-proof `resolveAsset` as the onboarding shell. Staff sign in with the uni better-auth session (`credentials: 'include'`, HttpOnly cookie — no token is ever read or stored by the app) and the signed-in state is proven by `GET /v1/auth/get-session` **plus** non-empty `staffRoles` from `/v1/me`, so it is server-derived rather than inferred from a missing login form. All eleven `/v1/admin/*` routes are wired; every response is parsed with the real `@sef/shared` schema and every request body validated before it is sent. Mutating calls need a session younger than 30 minutes, so `reauthentication_required` raises a re-auth banner (password + TOTP) and the person resubmits — nothing is replayed automatically. A 409 (`version_conflict` / `invalid_transition` / `already_enrolled`) renders a conflict panel with "Reload record" and the typed reason is discarded rather than retried; 403 renders a role refusal, and last-owner protection is surfaced, never routed around. Failures are shown as durable panels, not toasts. There is no administrative-export endpoint on the server yet, so "Export record" downloads the record already fetched and is labelled as such.

- **Programme and library views (PR-11):** the full curriculum is reachable at `GET /api/programme` on the engine, which proxies the uni's gated `GET /v1/programme` and validates it with `ProgrammeManifestResponseSchema` before rendering — an approved student gets the manifest, an unapproved one gets `503 programme_unavailable`, never a fabricated or empty curriculum. Semesters show rows with real nullable hours and zero credits, and separate the cross-semester support corpus (`number: 0`, `support: true`) from degree rows so it cannot inflate displayed totals. `content`/`release`/`selection` drive what is actionable: an `external` or `in_authoring` row is shown plainly with **no action**, because listing a row never implies permission to install it. `derivedCounts` is displayed beside the UI's own grouping, and option groups render as coherent bundles the server validates — a `409 invalid_transition` is a visible conflict, not an auto-retry.
- **Source ingestion limits, extraction and jobs (PR-13, part 1):** `engine/src/brain/sources/` holds the part that touches untrusted bytes. `limits.ts` enforces decoded-byte, PDF page, image dimension/pixel, extracted-character, job-concurrency and sources-per-job caps **before** anything is written or parsed — oversized input is refused, never truncated — and derives the on-disk filename from the source id so a client-supplied title can never reach a path. `extract.ts` is total: it returns a result describing what it managed rather than throwing into a job that cannot record why. A PDF over the page limit is refused *before* the first page is read; one unreadable page yields a **partial** result rather than losing the document; a scan with no text layer says so; and anything cut short sets `partial` with a reason, so truncation is never silent. `jobs.ts` enforces a legal stage machine (`extracting → awaiting_source_review → compiling → awaiting_review → committed|no_changes`), cancels in-flight work, refuses to revive a cancelled job, and retries only a failed one — from the *original* sources, so a retry re-extracts rather than resuming from half-finished derived text. Re-submitting the same source set reuses the live job instead of creating a duplicate. Schema violations surface as `JobStateError`, never as a raw `ZodError`.
- **Ingestion over HTTP (PR-13, part 2):** `POST /api/sources` takes a JSON envelope with base64 bytes rather than a multipart upload, so the size limit is enforced in exactly one place and the byte count is checked on the *decoded* data — base64 is round-tripped before it is trusted, because it decodes permissively. `GET /api/sources` returns jobs and source **summaries only**; it never returns source bodies. `POST /api/sources/:jobId/cancel|retry` map a missing job to `404` and an illegal transition to `409`, never to a silent no-op. The source is stored through `WikiStore.putSource` **before** anything is read out of it, so a failure mid-read keeps the material and the summary carries the reason. PDF reading uses `pdfjs-dist` pinned at `6.4.299` (legacy Node build, bundled standard-font metrics so text widths do not warn), and a malformed or password-protected document fails as `PdfParseError` rather than wedging the job. An image is kept and reported as "no text has been read yet" — local vision is not wired, and the UI is told so rather than given an invented reading.


- **Cumulative merge policy (PR-14, part 1):** `engine/src/brain/compiler/merge-policy.ts` decides what happens to a candidate claim against the page it would land on — `add`, `duplicate`, `supersede`, `dispute` or `reject_unsupported` — and decides it in code, from the existing claims and the citations the candidate carries. A model may propose any disposition; it cannot choose one. **Earlier supported knowledge is preserved by construction:** a restatement is recorded as a replacement rather than a duplicate so citations accumulate on one claim, and a claim that disagrees with one already there is `disputed` with both versions kept, so nothing is silently overwritten. An unsupported fact is refused whatever the text says. `planClaimMerges` is pure — `existing` is never mutated — and decides each candidate against the state the previous ones produce, so one bad candidate cannot poison the rest. The comparison drops stopwords before measuring overlap and requires two shared content words, because ratio alone files "The Sun makes all of the tides" against "The Moon makes the tides" as a new fact and quietly loses the contradiction.
- **Browser tests (PR-09 follow-up):** `pnpm test:e2e` runs Playwright against a **real** university server on port 4310, started by `e2e/global-setup.ts` and stopped afterwards. No mocks: the uni serves `/app` and `/device` itself, which is what makes the HttpOnly session cookie behave as it will in production. Six specs cover the onboarding surfaces and their hardening — the portal shell offering every account route, a **signed-out device approval being refused rather than faked**, malformed registration reported, framing refused on both pages, no script-readable session material, and traversal through the portal mount not reaching outside it. When the server cannot start, the specs **skip with the reason** rather than failing; the outcome travels through `test-results/e2e-status.json` because setup and workers are separate processes. Run `pnpm test:e2e:install` once to fetch Chromium. Artifacts land in `test-results/`.
- **Teacher boundaries are enforced before the model (PR-16):** `ConversationRegistry` issues the session and admits each turn — known, then owned by this student, then not closed, then this teacher, then not a replayed id, then not already in flight. Those checks and the in-flight claim run **with no `await` between them**, so two concurrent turns cannot both get through. `ConversationTurnSchema` has no `messages` field at all, which makes invented history structurally impossible rather than merely rejected. A handoff issues a **new** session rather than editing a teacher's identity on an open thread.
- **Capabilities are declared, not implied.** `packages/shared/src/teacher-policy.ts` declares 15 capabilities across context, tools, lesson lookup, wiki claims and attachments. Every tool registers for every teacher and asks the policy first, returning `{refused, capability, error}` and recording the refusal; a capability nobody declared is refused rather than silently absent. `read_lesson` is scoped to the teacher's own pool, so a lesson outside it reads as *not found*.
- **The Friend's privacy check covers images.** It previously ran only when there was **no** image attached (`req.teacher === 'friend' && !hasImage`), so an image skipped the check entirely. It now always runs, over the typed text *and* the attachment-derived text (filename and alt text), before the bytes move. Whatever the model reads out of an image is re-checked afterwards and refused if it leaks — extracted text is untrusted input, not a bypass.
- **The privacy pattern no longer refuses ordinary study questions.** The old catch-all matched any contact word anywhere before an `of`/`for`, so *"a sentence mentioning a number of students"* was refused as a privacy request. It is now three specific shapes, and bare "number" is held back because on its own it is a quantity. The apostrophe class spans ASCII, typographic and backtick forms, so a keyboard-autocorrected *roommate’s* is still caught.
- **Guide evidence is filtered per claim,** with withheld claims named in the rendered block rather than silently dropped, so one unsupported claim does not remove unrelated supported ones.
- **Philosopher is fully disabled** until PR-21 supplies anchors: the default resolver resolves nothing, so the seam fails closed loudly instead of improvising or making unconditional web calls.
- **Cohort sharing UI (PR-24):** the student shell gained a **Peers** view (`apps/desktop/src/features/peers/`): publish a vault page through a dialog whose preview *is* the network payload (the same `PublishShareRequest` object the engine POSTs), with the recipient cohort and the university-readable feed disclosed as required acknowledgements and attachment descriptors consented one by one — original bytes never upload. The cohort feed is cursor-paginated with preview/ignore; "Shared by me" lists withdrawn items too, and withdrawal copy says it stops future downloads without recalling accepted copies. Importing a peer share runs the normal source → compiler → proposal → student-review → apply pipeline, dedupes by share id + revision, and never writes the vault or mastery directly — the import lands in the same proposal-review affordance the Contribute desk uses. Offline, unsigned-in and refused calls are honest empty states. The registrar's Moderation tab now reads the session-staff surface (`/v1/admin/published-shares` list/detail/remove with note, cohort+state filters, keyset pagination, event trail) and keeps the quarantined pre-admission relay listed below it under its own label — removal needs a fresh staff session, so a view-only bearer sees the server's honest refusal rather than a fake success.
- **Contribute desk (PR-15):** `apps/desktop/src/features/contribute/` replaces the old Capture view with "Add to my wiki". Every contribution — pasted or written text, an uploaded PDF/photo, or a frozen conversation — lands first as an immutable source (`POST /api/sources`) carrying its provenance (`student` vs `external`, with creator/URL attribution for external material) and its original bytes fetchable at `GET /api/sources/:id/raw`. Extraction jobs pause at `awaiting_source_review`; the student can correct what a PDF or photo read (`PUT /api/sources/:id/extraction`, appended as an extraction revision), then a compile (`POST /api/sources/:jobId/compile`) always files a pending proposal — `autoAccept` is gone entirely, and `Reflect` only freezes the session's fresh turns as a source. The review dialog (`ProposalReviewDialog`) shows per-page diffs against the committed wiki, supports deselecting pages for a partial accept, and only `POST /api/proposals/:id/accept` writes. The Brain view gained a Sources panel, per-source detail with raw bytes and correction, and page revision history (`/api/brain/pages/:key/revisions`).
- **Evidence-checked answers (PR-17):** `engine/src/agents/evidence.ts` builds the set of what the teacher actually saw — citable ids for lessons, support notes, web results and fetched brain pages, non-citable ambient context, and claim verdicts whose withheld claims can be named but never asserted. `validators.ts` now classifies each answer segment (fact / belief / deduction / uncertainty / question) and checks every parsed citation: forged, wrong-owner, wrong-class, withheld and unsupported verdicts are named in the verification detail, and segments that fail are withheld before display rather than repaired or re-labelled. Factual text is buffered and only emitted once verification passes — progress and statuses stream, claims do not. The Philosopher's per-line `[course]`/`[web]` tagging and exactly-one-`Trailhead:` contract are enforced in the same assessment pass, and `[brain:]` citations resolve only for pages read with `brain_lookup` that turn.

## 7. Common tasks

**Add a course or lesson:** add markdown under `courseware/semester-<n>/<subject>/<course-id>/` with frontmatter (copy an existing lesson; the key fields are `courseId`, `lessonId`, `lessonName`, `releaseOrder`, `prerequisites` and `concepts`), restart the uni server, release it to a cohort in the registrar app, then install it from the student's Library. The version bump is what makes devices appear stale in Dispersal.

**Add a demo persona:** add the identity (id, email, cohort, stage, persona text) to `DEMO_PERSONAS` in `packages/shared/src/demo.ts`, and its brain script (heroes, misconceptions, links, sessions) to `engine/src/demo/personas.ts`. Then reset the demo data; both servers pick it up.

**Change a teacher's behaviour:** edit its brief in `engine/src/agents/prompts.ts`. If you add a rule, enforce it in `validators.ts` too. See the checklist in [docs/agentic-layer.md](docs/agentic-layer.md#8-changing-or-adding-an-agent).

**Tune source attribution:** the thresholds are constants at the top of `engine/src/agents/attribution.ts`; the tests in `attribution.test.ts` pin the behaviour.

**Point a role at a different model:** use Settings → Model roles and Providers (per role: tutor, brain, vision), or change the defaults in `.env`.

**Add an admin screen:** add a tab under `apps/desktop/src/features/admin/`, a route under `server/uni/src/routes/admin.ts`, and call `audit.record(actor, action, detail)` for every write.

## 8. Conventions

- **Logging:** structured JSON lines via `log.info('event_name', { fields })` in both servers. Use snake_case event names and never log passwords, tokens or API keys. `errorFields(error)` formats caught errors.
- **Errors:** routes return `{ error: string }` with a proper status code. The UI surfaces them through the query layer; don't swallow them silently.
- **Contracts first:** a request or response shape that crosses packages belongs in `packages/shared`.
- **Versioned roadmap DTOs:** `contracts.ts`, `identity.ts`, `programme.ts`, `wiki.ts`, `sharing.ts` and `teacher-policy.ts` in `packages/shared/src` add `schemaVersion: 2` shapes for admission, full academic rows, the source-backed wiki, cohort publication and message-only teacher requests. The programme shape is live: the uni server validates `courseware/programme-manifest.yaml` into it at boot (`loadProgrammeManifest` in `@sef/shared/node`) and serves it as `GET /v1/programme`; the others are additive only — no route or runtime consumes them yet. Shape validation proves structure, not ownership, entitlement or truth. Synthetic fixtures for tests are exposed only via `@sef/shared/testing` (never the root export), and the shared package's `node:test` suite runs under `tsx` like the engine and uni suites.
- **Files as the database:** JSON stores are written atomically (write to a temp file, then rename). Keep it that way, since the engine can be killed at any time on a laptop.
- **Tests:** `node:test` next to the code (`*.test.ts`). Run `pnpm test` and `pnpm typecheck` before committing.

## 9. Troubleshooting

| Symptom | Likely cause and fix |
| --- | --- |
| UI stuck on the boot splash | Engine not running or wrong `VITE_ENGINE_URL`. Check `pnpm dev:engine` output. |
| Teacher replies very slowly | Model loading for the first time, or thinking is on for the tutor. Run `ollama ps`; keep the tutor's thinking off. |
| Philosopher never cites `[web]` | SearXNG is down. Run `pnpm search:up`, then `curl localhost:8888`. |
| "Signature check failed" on install | The uni key changed after the engine pinned it. Reset the engine data (see Running it). |
| Profile can't sign in offline | It has never signed in online on this device. Sign in once with the uni server running. |
| A source chip opens the lesson but not the right spot | The heading index and the rendered headings disagree (for example, a heading inside a list). The reader falls back to matching the heading text; check the browser console for `section_not_found`. |
| Chat history empty after a demo reset | Expected: sessions live in `.data/engine/profiles/<id>/sessions/` and are re-seeded on the next boot. |
| Antivirus quarantines files in `node_modules` | A false positive on bundled binaries. Allow-list the project folder, then run `pnpm install` again. |

## 10. Known gaps and next steps

- Peer shares live in Postgres (published_shares) but are not end-to-end encrypted; legacy file-relay shares are quarantined pending explicit migration.
- The engine and the uni server trust the local network; there is no TLS in dev.
- The Tauri build doesn't yet bundle the engine as a sidecar (it expects the engine to be running).
- Source attribution is lexical (term overlap), not semantic; a heavily paraphrased answer can be under-credited. Seeded demo sessions have no stored sources.
- Retrieval is weighted keyword search, not embeddings. It's fine for about 500 lessons; a local embedding index is the natural next step.
- Ideas: spaced-repetition prompts from shaky stars, cohort-level anonymised misconception heatmaps for lecturers, and a vault export to Obsidian with one click.
